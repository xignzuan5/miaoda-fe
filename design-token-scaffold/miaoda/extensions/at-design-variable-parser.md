# @设计变量解析

这是给妙搭 Agent 使用的“设计变量解析”扩展定义。它负责发现和整理证据，不能把扫描到的每个值直接批准为正式 Token。

## 输入范围

优先读取当前项目中的以下内容：

1. `AGENTS.md`、`CLAUDE.md` 以及 `design-system/docs/` 下的规范。
2. `design-system/audit/` 下已有的 `raw-inventory.json`、`candidate-tokens.json`、`structure-inventory.json`、`layout-inventory.json`、`font-inventory.json` 和 `audit-report.md`。
3. 主题入口、全局 CSS、CSS-in-JS、Tailwind 或 UI 库配置、组件覆盖、字体资源、路由、菜单和多个代表页面。
4. 运行时页面中实际生效的样式；声明了 `font-family` 不等于字体已经加载，必须检查资源和浏览器结果。

如果用户通过 `@文件解析` 附加了项目外部的 Markdown、CSS、JSON、HTML、图片或表格，也要把它们作为有来源的证据处理，并记录文件名。已经随项目导入的 `design-system/` 文件必须直接从项目代码读取，不要要求用户重复附加。

## 两阶段执行协议

### 第一阶段：确定性扫描

如果当前妙搭开发环境提供项目命令执行能力，必须先在项目根目录执行：

```bash
npm run project:init
```

命令成功的最低证据是：进程返回码为 0，并且项目中实际更新了 `design-system/audit/` 与 `design-system/dist/`。必须回显命令输出、扫描统计和产物路径；只看到 Agent 的文字描述不能算扫描成功。

如果当前环境没有终端或项目命令执行能力，不得声称已经完成扫描，也不得把语义分析结果伪装成扫描结果。此时明确报告“确定性扫描未执行”，只能读取项目中已有的 `design-system/audit/`，或等待用户/CI 提供最新产物。

### 第二阶段：语义沉淀

仅在第一阶段成功，或项目中已有带来源的最新审计产物时，继续进行语义归类、Token/Recipe/模板沉淀。扫描器负责事实盘点，模型负责上下文语义；两者的输出必须分开记录。

## 解析规则

1. 覆盖项目实际出现的颜色、透明度、排版、字体族、字重、字号、行高、字距、间距、尺寸、边框、圆角、阴影、层级、动效、滚动、溢出、定位、断点、密度、主题模式和交互状态。
2. 硬编码值可以提取。先记录原值、出现次数、文件位置、选择器/组件、上下文和计算后的实际值，再判断它是 Primitive、Semantic、Component、布局常量、数据值还是一次性例外。
3. 结合语义 HTML、ARIA、组件名、变量名、选择器、父子关系和页面位置推断用途。例如 `h1/h2`、表头、单元格、导航激活态、禁用态和错误态可以作为语义证据，但只能标为“候选”直到源码或运行时确认。
4. 相同数值出现在不同用途时不得合并。相同用途使用不同值时建立分组并报告冲突，不得用平均值或经验值替换。
5. 读取已有主题入口和组件覆盖的优先级；源码和运行时与旧审计冲突时，以源码和运行时为准，并回填审计。
6. 同时识别公共 AppShell/Layout、内容插槽、路由/菜单/面包屑装配点，以及实际存在的列表、选项卡、表单、详情、仪表盘、两列和三列内容网格模式。
7. 两列和三列只沉淀列容器、轨道比例、断点、间距、对齐、折叠和插槽；禁止把某个业务页面的字段、文案和数据复制进通用模板。
8. 遇到多个互斥解释、缺少主题模式或无法确认运行时效果时，保留多个候选并标记 `unresolved`，不要猜测。

## 产物

在当前项目中维护或生成：

- `design-system/audit/`：原始值、结构、布局、字体、来源位置和覆盖缺口。
- `design-system/src/tokens/`：经过语义确认的 Primitive、Semantic、Component 和主题 Token。
- `design-system/src/recipes/`：组件状态、部件映射和使用约束。
- `design-system/src/templates/`：可编译的公共壳层和内容模板，使用插槽/Props 表达业务变化。
- `design-system/audit/page-templates.json`：模板来源、适用场景、插槽、不可变区域、依赖和验证状态。
- `design-system/docs/design-spec.md`：中文设计规范、已确认规则、例外和待决项。
- `design-system/audit/migration-map.json`：硬编码或旧变量到建议 Token 的迁移映射。

每条正式 Token 必须带类型、值或别名、中文描述、来源证据、状态和适用模式。无法确认的内容只能放在候选或待决区，不能写入已批准区。

## 完成检查

完成后运行项目规定的 Token 校验和构建，检查亮色/暗色/高对比度、字体实际加载、焦点/禁用/错误/加载态、响应式和页面壳层。用中文说明：读取了哪些来源、提取了哪些类别、哪些是硬编码、哪些已转为正式 Token、哪些仍未验证。

## 在妙搭中使用

如果当前租户支持自定义 `@` 插件，把本文件的元数据和“解析规则/产物/完成检查”作为插件说明；如果 `@` 菜单只有官方插件，则使用 `@文件解析` 附加本文件和审计资料，再发送：

```text
请按附件中的“@设计变量解析”规则，读取当前项目源码和 design-system/audit/，完成一次有来源的设计变量解析。硬编码值也要提取，但不得未经语义确认直接批准为正式 Token。完成后更新 Token、Recipe、页面模板登记和中文设计规范，并运行校验和构建。
```
